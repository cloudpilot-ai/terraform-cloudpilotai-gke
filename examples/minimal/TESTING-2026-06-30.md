# Minimal GKE Example Test Record (2026-06-30)

This document records the end-to-end validation of the `examples/minimal` flow against a real GKE cluster.

## Target

- Project: `cloudpilot-ai-dev`
- Location: `us-central1`
- Cluster: `qyh-gke-test-0630`
- Example directory: `examples/minimal`

## Goal

Validate the full minimal-example lifecycle:

1. install
2. update
3. uninstall

using the minimal-input path as much as possible.

## Inputs Used

The test intentionally used only the minimal required Terraform inputs in `terraform.tfvars`:

```hcl
cluster_name = "qyh-gke-test-0630"
region       = "us-central1"
```

The CloudPilot API key was passed through the environment instead of writing it into a tracked file:

```bash
TF_VAR_cloudpilotai_api_key=...
```

The following optional inputs were left unset on purpose during the main install flow:

- `project_id`
- `cluster_uid`
- `cluster_location`
- `kubeconfig`

This verified that the provider could infer:

- `project_id` from the active local `gcloud` project
- `cluster_uid` from `kube-system` namespace UID after kubeconfig became available

### Issues Found During Install

#### Issue 1: cluster setting empty-string normalization bug

The first apply failed with:

```text
Error: Provider produced inconsistent result after apply
...
.cluster_setting.post_run_command: was null, but now cty.StringVal("")
.cluster_setting.pre_run_command: was null, but now cty.StringVal("")
```

Fix applied:

- preserve `null` for `pre_run_command` and `post_run_command` when the remote API returns empty strings and the user did not configure those fields

#### Issue 2: minimal example still effectively required `cloudpilotai_api_endpoint`

The example `variables.tf` still had no default for `cloudpilotai_api_endpoint`, which contradicted the minimal-input documentation.

Fix applied:

- set `cloudpilotai_api_endpoint` default to `https://api.cloudpilot.ai`

#### Issue 3: install path should infer `project_id` and `cluster_uid`

The provider was updated so that fresh GKE installs can:

- infer `project_id` from the current local `gcloud` project
- infer `cluster_uid` from the `kube-system` namespace once kubeconfig is available

## Update Flow

### Temporary Update Used For Testing

To exercise both cluster and node-autoscaler update paths, the example was temporarily changed to:

- change `cluster_setting.discount` from `0.15` to `0.20`
- add a temporary label to the `cloudpilot-general` nodepool:

```hcl
labels = {
  codex-test = "update-1"
}
```

### Commands

```bash
terraform plan -no-color
terraform apply -auto-approve -no-color
terraform plan -no-color
```

### Initial Update Plan

The update plan correctly showed two in-place updates:

```text
# module.cloudpilotai_gke.cloudpilotai_gke_cluster.this will be updated in-place
~ discount = 0.15 -> 0.2

# module.cloudpilotai_gke.cloudpilotai_gke_node_autoscaler.this[0] will be updated in-place
+ labels = {
    "codex-test" = "update-1"
  }
```

### Issue Found During Update

The first update apply failed with:

```text
Error: Provider produced inconsistent result after apply
...
.nodepools[0].labels: new element "node.cloudpilot.ai/managed" has appeared
```

Root cause:

- the server injects `node.cloudpilot.ai/managed=true`
- the provider was incorrectly treating that server-managed default label as if it were user-configured state

Fix applied:

- preserve only the user-managed map keys from state during post-write hydration
- ignore extra server-default labels such as `node.cloudpilot.ai/managed`

### Final Update Result

After the fix, the update apply completed successfully:

```text

Apply complete! Resources: 0 added, 1 changed, 0 destroyed.
```

Follow-up validation:


Key output:

## Uninstall Flow

### Commands

```bash
terraform destroy -auto-approve -no-color
```

### Destroy Issues Found

#### Issue 1: GKE restore script had previously been interactive

This had already been fixed earlier in the session before the minimal E2E run:

- default destroy no longer enters an interactive restore flow
- restore now only runs when explicit restore sizes are configured

Observed behavior in this test:

- destroy started immediately
- no `Please input the desired size ...` prompt appeared

#### Issue 2: remote default `cloudpilot-gpu` nodepool blocked nodeclass deletion

The first destroy run failed after Workload Autoscaler uninstall succeeded:

```text
Error: failed to delete tracked gke nodeclasses
DELETE https://api.cloudpilot.ai/api/v1/rebalance/clusters/.../nodeclasses/cloudpilot
giving up after 5 attempt(s): status 500
```

Direct API verification showed the root cause:

```text
gcenodeclass cloudpilot is referenced by nodepools [cloudpilot-gpu cloudpilot-general], please delete the nodepools first
```

Root cause:

- the install flow created a managed default `cloudpilot-gpu` nodepool remotely
- it was not part of Terraform state because the minimal example only declared `cloudpilot-general`
- destroy deleted only tracked nodepools, then immediately tried to delete the shared nodeclass

Fix applied:

- during GKE Node Autoscaler destroy, list remote nodepools
- delete additional CloudPilot-managed remote nodepools that still reference tracked nodeclasses
- then retry nodeclass deletion

### Final Destroy Result

After the fix, destroy completed successfully:

```text
module.cloudpilotai_gke.cloudpilotai_gke_node_autoscaler.this[0]: Destruction complete after 2s
module.cloudpilotai_gke.cloudpilotai_gke_cluster.this: Destruction complete after 2m44s

Destroy complete! Resources: 2 destroyed.
```

## Summary

The minimal example lifecycle was validated successfully on `qyh-gke-test-0630`:

- install: passed
- update: passed
- uninstall: passed

The validation also surfaced and fixed several real provider/module issues:

1. infer `project_id` from local `gcloud`
2. infer `cluster_uid` from `kube-system`
3. default `cloudpilotai_api_endpoint` in the minimal example
4. preserve `null` for empty cluster setting commands
