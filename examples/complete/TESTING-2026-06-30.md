## Destroy With Restore

Before destroy, the helper workload deployment was deleted, but the managed nodes were intentionally left in place so restore had real work to do:

```bash
kubectl delete -f trigger-managed-node.yaml
```

### Commands

```bash
terraform destroy -auto-approve -no-color
```

### Provider / Module Fixes Required

During this validation, the restore workflow exposed an ordering problem:

- the old flow restored regular GKE nodepools inside `cloudpilotai_gke_node_autoscaler`
- CloudPilot components were still running at that time
- this let optimizer activity interfere with regular nodepool convergence

To fix that, the destroy flow was changed so that:

1. `cloudpilotai_gke_node_autoscaler` no longer performs module-driven restore
2. the module maps EKS-style `skip_restore` / `restore_node_number` to the GKE cluster resource
3. `cloudpilotai_gke_cluster` now:
   - uninstalls CloudPilot components first
   - then runs restore
   - then performs best-effort remote API cleanup

This matches the EKS mental model much more closely.

### Destroy Result

Final destroy output:

```text
module.cloudpilotai_gke.cloudpilotai_gke_node_autoscaler.this[0]: Destruction complete after 2s
module.cloudpilotai_gke.cloudpilotai_workload_autoscaler.this[0]: Destruction complete after 1m1s
module.cloudpilotai_gke.cloudpilotai_gke_cluster.this: Destruction complete after 10m20s

Warning: skipped deletion of recommendation policy balanced

Destroy complete! Resources: 3 destroyed.
```

The recommendation policy warning was acceptable for this test because the provider now intentionally prioritizes successful uninstall over perfect remote config cleanup.
